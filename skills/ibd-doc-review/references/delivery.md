# 章节复核交付约定

> 本文是「章节复核类委托」的交付形态与职权规范。**触发**：用户说「研究下XX节，帮我看看描述逻辑、语法有没有错误」等复核类指令。
> 细则来源：用户级长期记忆（补批注纪律），迁入本文件；记忆侧只保留铁律摘要。

---

## 零、进门第一档：检查项声明（先声明，再动手）

> **动因**：粗颗粒的「查格式／查内容／查财务」回答不了「到底查了什么」——复核覆盖面若无显式声明，就落入模型随机性：同一份稿两次复核查出两套东西，用户既无法判断结论覆盖到哪、也无法对照验收。**未声明即未约束。**

**顺序铁律**：任何复核委托，**动手第一步**是输出《本轮检查项声明》，然后才谈交付形态与深度。**三要素采「反问确认制」**：**每份文档首次复核委托时，AI 就三要素各出一问（合并为一张三行小表，不拆三连问），每问附推荐项**（推荐＝批注版／标准深度）；用户确认或改选后才动手。**同一文档内后续委托沿用已确认组合、不再反问**（不限时间）；**换文档 ⇒ 重新三问**；用户中途明示改任何要素即刻生效并作为该文档后续新默认。**措辞纪律**：三问表**人话为主、编号只作括注**（模板 → [check-scope.md](check-scope.md) §六）。

| 顺序 | 事项 | 说明 |
|---|---|---|
| **第一档** | **检查项声明** | 查哪些项／不查哪些／为什么——**明细清单与模板 = [check-scope.md](check-scope.md)** |
| 第二档 | 交付形态 | 批注版／文本定稿／修订稿（§五）——**反问确认，推荐批注版** |
| 第三档 | 深度档位 | L1/L2/L3——**反问确认，推荐 L2 标准预填**（§七） |

**声明单四要素**（模板见 [check-scope.md](check-scope.md) §六）：

1. **检查**——本次实际要跑的项，**按域 ＋ 性质**列编号（A 文字格式／B 内容质量／C 财务〔细分 **C-P 专业判断 / C-Q 数值正确性 / C-D 执行要求**〕）
2. **不查**——跳过的项**逐项点名 ＋ 原因**（写「未查」不算，要写清为什么）
3. **特别专项**——S1 读取前置／S2 片段模式／S3 敏感议题／S4 数据基准，命中情况写明
4. **交付前将跑**——域 F 交付件核验（自动执行，不进勾选；**E 行业为预留域，未启用不提**）

**三条纪律**（与 SKIP 同纪律——静默缩范围＝静默失败）：

- **未核即声明**：跳过项必须点名，不许用「默认全查」蒙混过去
- **首尾一致**：动手前的声明 ⟷ 交付报告头的范围声明（§八）必须是**同一份**；中途增减项须**重新声明一次**，不许悄悄改
- **档位只是预设**：L1/L2/L3 只给默认勾选组合，用户点名加减某项一律照办

**唯一的简化情形**：命中 S2 片段模式时，声明单可以变短（只列本段可核的子集 ＋ 跳过的全文性项），但**「先声明再动手」本身不免除**。

**用户原话**（存档）：

> 「我觉得查什么东西需要再明细展开区分，要在每次检查前声明，上提到第一档」

## 一、默认交付形态 = 批注版原文 + 复核报告（Excel）；总览只作中间件

**一主一配 ＋ 一件中间件**：

- **主交付物**：章节复核结论以**原位批注**打在原文对应位置——载体自适应：
  - docx 原文 → Word 审阅批注
  - 仅 PDF → PDF 高亮注释
- **配套交付物（人读报告）＝ 复核报告**，**Excel（`.xlsx`）** 形态、按**问题性质分工作表**，编号与批注**一一对应**。
  规格见 **§八之二**；执行器 = `ibd-doc-annotate/scripts/review_report_to_xlsx.py`。
- **中间件（不交付用户）＝ 批注总览 md**：注入器同链路产出 `<输出>_批注总览.md`，供程序读取／检索归档／兜底未锚定索引；
  **不再产 Word 版**（`--overview-docx` 链路已撤除），**也不作为交付物列给用户**。
- **不主动扩展**：除非用户明确说「生成修订稿」，否则**不主动生成修订稿、不主动推进数据复核/法律复核等后续环节**

## 二、执行链路

```
复核问题清单 + 原文
  → ibd-doc-annotate 注入（脚本自动编号 J/L/I/Z+序号、锚点定位、4 行紧凑排版）
  → ibd-doc-review deliver_gate.py --annotated 门禁（含基础十项 + 批注两项）
  → 交付
```

**门禁是硬关卡**：门禁返回非 PASS 一律退回 `ibd-doc-annotate` 重注入，不得带瑕疵交付。

> **多轮迭代加一步**：本轮不是第一轮时，出清单后先跑 `round_diff.py --prev <上轮清单> --cur <本轮清单>`（§七之二），
> 产出轮次台账随报告附页交付——**不跑就等于只报「这轮还剩什么」，报不出「上轮的东西动了没有」**。

**推荐一条命令跑完**（基础十项 + 批注两项，共十二项）：

```bash
python scripts/deliver_gate.py --docx <批注版.docx> --annotated --expect-annotated <条数> \
       [--md <内容源.md>] [--anchors "36,507.55;19.96"]
```

`--annotated` 已覆盖 `check_annotations.py` 的 **docx 侧**全部硬性断言（部件 / 结构 / 编号）；只有 **PDF 侧**高亮注释校验仍需单独跑 `check_annotations.py --pdf`。修订稿同理：`deliver_gate.py --revised [--expect-revised N]` 覆盖 `check_revisions.py --mode revise` 的全部断言（含落定证明）。

## 三、批注/修订职权划分

| 产出形态 | 归属 skill | 说明 |
|---|---|---|
| **批注版**（原位批注） | `ibd-doc-annotate` | 复核落地形态之一 |
| **修订稿**（直接改好原文文字） | `ibd-doc-annotate` | 与批注同源、同为复核落地形态 |
| **格式修订**（套样式链路） | `ibd-doc-review` | `check_styles.py --revise`，**与内容复核无关** |

**修订稿执行器**：`ibd-doc-annotate/scripts/revise_docx.py --mode`
- `revise` = Word 修订模式（留痕）
- `clean` = 直接改好（无痕）
- `both` = 双版

按提示词区分模式；修订规范 = 本文所属 skill 的 [revisions.md](revisions.md)；门禁 = `deliver_gate.py --revised`（等价覆盖 `check_revisions.py --mode revise`）。

## 四、只加批注不改原文（红线）

- 注入**不改动原文任何文字**
- 锚点段落含**复杂 run**（换行/制表）或**骑跨超链接** → **不自动注入**，记入批注总览 md「未锚定」条目（中间件兜底），交人工定位
- 格式单一事实源：批注正文结构 / 编号规则 / 10 类类型词表 / 字体 / 锚点规则 → [annotations.md](annotations.md)
  - 正文 4 行紧凑无空行；标签行/标题行加粗；问题描述与建议仅引导词加粗

## 五、触发语与路由（三形态）

| 用户措辞 | 路由 |
|---|---|
| 「研究下XX节，帮我看看描述逻辑、语法有没有错误」 | **批注版形态**：默认输出**批注版 + 复核报告（Excel）**（总览 md 降为中间件、不交付）——前提：该项目未声明过形态 |
| 「问题X定稿」「逐条列修改点」「直接给文本」「给出修改后文本」 | **文本定稿形态**：逐条「原文→改后」对照输出（不进批注、不出修订稿、不出独立审核报告）；清单条目 `rev` 字段全量填充（可粘贴定稿文本） |
| 「生成修订稿」「出一版修订稿」「直接改好」… | 进入修订流程，但**先反问形态**（revise / clean / both）再执行 |

**铁律 1（形态三选一）**：批注版／文本定稿／修订稿三形态互斥，一次委托只出一种；文本定稿形态是批注版的**对等替代**（不是降级）。

**铁律 2（文档级确认记忆）**：**每份文档首次复核委托，形态作为三要素反问之一确认**（附推荐「批注版」）；**同一文档内后续委托沿用已确认形态、不再反问**（不限时间）；**换文档 ⇒ 重新确认**；用户明示改形态 ⇒ 即刻生效并作为该文档后续默认。**铁律 3（修订先反问）**：不按措辞直接路由到修订——任何修订类说法都必须先确认 revise/clean/both，避免猜错模式导致返工。

**铁律 4（文本定稿形态 = 清单 `rev` 字段全量填充）**：文本定稿形态的交付物不是「问题清单」，而是**可直接粘贴的定稿文本**——清单条目 **`rev` 为必填**（承载「改后」全文）、**`advice` 可省**；输出按条目排列「原文 → 改后」对照。schema 层已用 `anyOf` 表达该条件：`advice`／`rev` **二者至少其一**（`problems.schema.json`）。
- **rev ≠ advice**：`advice` 是**指令式建议**（「核对…后统一…」），`rev` 是**可直接粘贴的文本**——复核员在文本定稿形态下同时承担「改稿建议人」角色，故 rev 升为主交付物、不再是例外。
- **一条链路两种用途**：rev 字段亦为修订稿形态（`ibd-doc-annotate/scripts/revise_docx.py`）的替换源——「今天给文本、明天要修订稿」无需重做。

## 五之二、复核 → 写作回流（P6）

复核发现的落地形态有三条去向，**不得混淆**：

| 去向 | 载体 | 触发 |
|---|---|---|
| 原位批注 | `ibd-doc-annotate` 注入 docx/PDF | 批注版形态 |
| **可粘贴定稿文本** | 清单 `rev` 字段（逐条） | 文本定稿形态（**常态**，非例外） |
| 修订稿（留痕/无痕） | `revise_docx.py --mode revise/clean` | 用户明确要求 |

> 复核产出**如何喂给改稿**是有定义的：`rev` 即为标准接口。缺 rev 的条目不得静默丢弃——入总览「待定稿」清单。

## 五之三、聊天流顺稿对照卡（show_widget 高亮格式）

> **定位**：用户**逐段粘贴文本**（非整份 docx）做聊天流顺稿复核时的**回复渲染格式**。适用判据：① 输入为对话内粘贴片段而非文件；② 产出为「每段问题定位＋改后全文」。docx 文件级复核不适用（走批注版/文本定稿/修订稿三形态，§五）。
> **驱动案例**：2026-10-16 现场核查问询回复逐段顺稿——用户先要求「修改处加粗」，仍反馈看不清，改用高亮对照卡后确认「这个卡片的形式挺好」，裁定固化。

**格式规则**：

| 项 | 规则 |
|---|---|
| 载体 | `show_widget`（HTML），每段一张对照卡；纯文本回复只放结论行与待确认项汇总，**不重复贴全文** |
| 增删标注 | **新增/修改＝绿底高亮**（dark 主题用 c-teal 800 底＋200 字）；**删除＝红底删除线**（c-red 800 底＋删除线）；标点级微调同规则、不豁免 |
| 卡片结构 | 段落标题行 → 原文全文（内嵌标注）→ 灰字说明行（问题定性＋建议级/待确认标记） |
| 无修改段 | 单独一行明确「本段无需修改」，不出卡 |
| 待确认项 | 卡内灰字逐条标注【待确认】，**回复末尾汇总**待拍板清单（编号） |
| 跨节一致性 | 同源表述在不同段出现措辞分歧（如「整合效果/整合效应」）→ 当场举手列编号，不擅自统一 |
| 主题适配 | 遵 IDE 主题（dark：深底浅字；light：浅底深字）；删除线厚度 1px，段落 line-height ≥1.9 保证批注可读 |

**格式演进纪律**：用户在会话中途改格式（加粗→高亮卡），**当轮起全量按新格式执行**，已交付节次仅在用户点名时回溯重发，不主动重发。

## 六、批注纪律（跨项目）

- **全量进批注**：确认的问题**不分大小全部进批注**（批注体现全量）
- **清单照常保留**：问题清单 / 复核报告**与批注并行交付**，编号一一对应（批注总览 md 为中间件，兜底未锚定索引，不单列为交付物）
- **被禁止的只有一种**：只进清单、不批注
- **覆盖单元 = 根因问题**：同源连锁错误**合为一条**，位置由清单兜底（不是每个表象各批一条）
- **条数上限**：单文件 ≤200 条；>400 条**拆分交付**——超限处置是**拆/并，不是删条目**

**用户原话**（存档）：

> 「错误不分大小都要批注」
> 「批注要体现全量，清单本身还是要留的」
> 「全量覆盖也不能个个都批」

**细则落点**：`ibd-finance-review` execution-discipline 铁律 2 + 细则 9、issue-list-format §1.1、`ibd-doc-annotate` validate_issues、[annotations.md](annotations.md) §3。

**驱动案例**：某芯片设计项目 v3 遗留 7 项低危 → v4 全部转批注 Z-12~Z-18。

## 七、复核深度档位（L1/L2/L3 · 声明单的默认预设）

> **定位（2026-09-28 起）**：档位**不再是独立于检查项的第二套选择**，而是 [check-scope.md](check-scope.md) §七那张「默认勾选组合」表的别名——选定档位＝把声明单预填一遍，**预填之后仍可逐项加减**。这样「深度」与「查了什么」说的是同一件事，不会出现「选了 L3 却漏了某项」的口径裂缝。
> **为什么原本要有档位**：复核精细度若无显式定义即落入模型随机性（同委托产出粒度时大时小）——**未定义即未约束**。深度是委托的显式参数，不是 AI 的临场发挥。

> **分档轴 ＝ 性质**（2026-09-29 用户校正）：**L2 装「机器能判的」**（格式规范／数值正确性／执行要求）；**L3 装「只有人能判的」**（专业判断）。

| 档位 | 名称 | 做什么 | 不做什么 | 适用场景 |
|---|---|---|---|---|
| **L1 快扫** | 表面核对 | 标点/错别字/明显数字错误/禁词扫描 | 不做勾稽、不逐数登记、不出台账 | 定稿前最后一遍过；片段粘贴快速过 |
| **L2 标准**（**默认档**） | 数字与格式全核 | L1 ＋ A 域全项 ＋ B1–B8（含 **B6/B7 交稿前自检与自评**，随交付步执行）＋ **五类机械勾稽全算（C-Q 全量）＋ 逐数台账（C-D，零未核项）** ＋ 问题清单全量输出 | **不做专业判断（C-P）——不出「会计处理是否恰当」的意见** | 章节复核常规委托（未声明深度时） |
| **L3 深核** | 专业判断 | L2 ＋ **C-P 专业判断全 16 维**（`ibd-finance-review` 维度走查，AI 只提质疑）＋ **D 法律惯例对照全 22 项**（`ibd-legal-review` 承载，只对照不定性）＋ **（预留）行业专业复核** | —— | 需要会计处理／法律／行业**判断意见**时；问询回复定稿 |

**路由与声明**：
- 触发语映射：「快速过一遍」「扫一眼」→ 推荐 L1（仍走三要素反问确认）；用户表态档位 → 照办；**未表态 → AI 推荐 L2 并反问确认**（不再静默默认）。
- **模糊时反问一问**（与修订形态反问同纪律）。
- **档位落地方式 = 预填声明单**（§零）：报告头与该声明单**同一份**——「本次复核深度＝L2 标准（含勾稽与台账，未含会计专业判断）」。声明未做与声明 SKIP 同纪律（静默降档＝静默失败）。
- **升档随时可加**：L2 交付后用户要求「再深核一遍」→ 在 L2 产物之上补 L3 差量，不重跑 L1/L2。

## 七之二、跨轮次状态追踪（`round_diff.py` · 多轮迭代专用）

> **什么时候用**：同一章节**第二轮及以后**的复核（改一版 → 全量重核 → 再改）。L2 档位迭代最常见。
> **为什么要有**：多轮复核若每轮都从零出清单，就没人回答得了「上轮 20 条里哪几条改好了、哪几条没动、这轮又新冒了什么」——此前只能人工对着两份 Excel 数。**一轮复核的真实交付价值，一半在清单、一半在收敛**。

```bash
# ① 出台账（md 供人读；--json 供报告生成器消费）
python scripts/round_diff.py --prev <上轮清单.json> --cur <本轮清单.json> \
       --out <轮次台账.md> [--round 3]
python scripts/round_diff.py --find-prev <清单目录> --cur <本轮清单.json> --json > <台账.json>

# ② 并进报告（ibd-doc-annotate 的生成器：出「轮次状态」工作表，紧跟封面）
python ../ibd-doc-annotate/scripts/review_report_to_xlsx.py --issues <本轮清单.json> \
       --meta <报告元信息.json> --round-ledger <台账.json> --out <报告.xlsx>
```

**清单留档规约（不照做，下一轮就没得比）**：每轮清单存**与报告同目录**，命名
`<原文名>_<YYYYMMDD>_v<N>_issues.json`（如 `XX公司_招股书第X节_20261018_v1_issues.json`），
**全轮次不删**（单份 3–8 KB，一个章节跑十轮也就几十 KB）。名字里的日期＋`vN` 不是装饰——
`--find-prev` 就靠它认出上一轮；目录里同时躺着报告 xlsx、meta json、台账 md，
**按修改时间或「最新 JSON」挑都会认错文件**。认不出时脚本**报错并停**，不猜。

**匹配键＝`anchor`**（原文问题句段的精确子串）：先归一化（全角转半角、去空白与标点、小写），
完全一致即命中；否则算相似度取最高者。**`title` 不作匹配键**——同标题不同段落的问题很常见。

| 档 | 判据 | 含义 | 谁下结论 |
|---|---|---|---|
| **未修复·原句未动** | 归一化后完全相同 | 原句一字未改，问题照旧 | 机器 |
| **未修复·已改写** | 相似度 ≥ `--hi`（默认 0.85） | 句子动过（改数字／换措辞），**本轮复核仍标出** ⇒ 问题仍在 | 机器 |
| **疑似已关闭** | 相似度 ∈ [`--lo`, `--hi`)（默认 0.60–0.85） | 措辞大改、本轮未逐字命中 | **人工**（脚本退出码 1 提醒） |
| **已关闭** | 相似度 < `--lo` | 原句已不存在，本轮亦未再报 | 机器 ＋ 对照范围声明 |
| **新增** | 本轮条目未匹配到上轮任一条 | 本轮新发现 | 机器 |

**三条硬约束（否则台账会被误读）**：

1. **前提是「本轮清单＝本轮复核判定仍然存在的问题」**。所以「上轮条目在本轮清单里出现」≡「问题还在」，差别只是原句动没动。**前提不成立（例如本轮只抽核了一部分）时，不得用本脚本算关闭率**。
2. **「已关闭」≠「已改好」**：整段删除、问题转移、**本轮复核范围收窄**（L2→L1、只核财务域）都会造成「已关闭」。故交付时须与报告头的**范围声明**（§八）逐项对照；范围有变，台账内「已关闭」一律标「不可比」。
3. **台账里「疑似已关闭」一档禁止直接写成「已修复」**。该档存在时脚本退出码为 1——这是刻意设计，别当噪声消掉。

**并入交付**：轮次台账作为复核报告的附页（Excel 第二工作表「轮次状态」，或独立 md 随附）——
传 `--round-ledger` 即生成该页（第二页，紧跟封面；不传则**不出空页**，空页会被读成「本轮无遗留」），
**不进批注版原文**（原文只放本轮仍存在的问题）；报告头补一行「本轮为第 N 轮，上轮 N₀ 条，
未修复 X（原句未动 Y／已改写 Z）／疑似关闭 P／关闭 Q／新增 R」。

## 八、报告头范围声明（与进门声明首尾一致）

> **范围选择器（域 × 子项）**已升格为进门第一档，明细见 [check-scope.md](check-scope.md)、动作规范见本文 §零。本节只留报告头的**落款义务**：凡非「全项」复核，交付报告头必须显式写明——「本次核对范围＝财务勾稽（域）；**未核：文字与格式／内容质量／禁用词**」。**动手前声明什么，报告头就写什么**，两处不一致即视为静默缩范围。

**收尾四段式**（所有工作流统一，复核线的展开体＝问题清单）：

1. **结论行**——✅/⚠️ ＋ 一句话（几处必改/几处待确认）
2. **做了什么**——对照三问确认逐项收口（范围/形态/深度各一行交付实况）
3. **证据读数**——问题清单（编号｜类型｜严重度｜位置用原文锚点）；批次条目形态见 [annotations.md](annotations.md)
4. **行动项**——三选一：无需处理／等你改完贴回复验／待你给口径

> **落款义务**：本节要求的报告头范围声明是**三处同一份**——动手前的声明单 ⟷ 对话回复头 ⟷ **复核报告的「封面与汇总」页**（§八之二）。报告是一份**独立文件**，脱离对话被单独流转，故范围声明必须随报告走。

## 八之二、复核报告（Excel）交付形态

> **定位**：复核报告 ＝ 复核交付的**人读报告本体**。三件易混物先分清——§一 的**批注版原文**是「结论打在原文上」的载体；**批注总览 md** 是中间件（不是报告、也不交付）；**§八「收尾四段式」** 是**对话回复**的话术骨架，**本节才是报告文件**的骨架。
> **口径来源**：复核报告用 **Excel** 形态——可按**问题性质分成不同工作表**，比单一 Word 报告更便于分性质复盘；批注总览只需 md 作**中间文件**，不作最终输出。
> **执行器**：`ibd-doc-annotate/scripts/review_report_to_xlsx.py`（清单 JSON → xlsx）。**规格在本节，生成逻辑不另立**。

**工作簿结构（三类工作表）**

| 工作表 | 内容 |
|---|---|
| **封面与汇总** | 报告头（复核对象／唯一数据基准／复核方式／复核结论）＋ **复核声明** ＋ 结论与统计（按严重度·按性质·按域）＋ 复核范围与方法 ＋ 已核查通过 ＋ 质量证据 ＋ 行动项 |
| **轮次状态**（可选） | 多轮复核时（传 `--round-ledger`）出现，紧跟封面：五态台账 ＋ 统计。规格见 §七之二；判据只填**台账给的事实**，不代写结论 |
| **按性质分页** | 一张工作表一个「问题性质」，条目按严重度降序排列 |
| **全部** | 不拆分的完整清单，便于整体排序筛选 |

> 封面**仅主标题一行跨列居中**，其余标题（副标题、小节标题）一律**左对齐**；小节序号（一、二、…）按**实际渲染顺序**自增——某节无内容而缺省时不留空号（防「一、三、四」跳号）。
>
> **上下等宽**：封面所有行一律铺满 **A:C** 三列——文本行（标题／条目／声明）跨 A:C 合并；键值行值格合并 B:C；统计表若不足三列，末列**右延并合并**到 C。列宽 A:B:C **唯一一套**（不随内容变），故封面左右边界通栏对齐。

**「复核声明」节（必须随报告走）**

报告是一份**独立文件**、会脱离对话单独流转，故 §八 说的「动手前声明什么、报告头就写什么」在此落地为**封面第三块**（`ibd-doc-annotate` 的 `--meta .declaration` 渲染）。内容 ＝ [check-scope.md](check-scope.md) §六《本轮检查项声明》的**四栏结构**：

| 栏（meta 键） | 写什么 |
|---|---|
| 复核深度（`depth`） | 本次深度档位（L1/L2/L3）或自定义，人话表述 |
| **检查**（`checked`） | 本次实际跑的项，**按性质列**（格式规范／数值正确性／表达与事实／专业判断／执行要求） |
| **不查**（`not_checked`） | **点名 ＋ 原因**——跳过的每一项都要点名，不许静默缩范围（与 SKIP 同纪律） |
| 特别专项（`special`） | 由输入触发而生效的特例（片段模式／敏感议题只标注等），无则整键省略 |
| 交付前将跑（`gates`） | F 域交付件核验——**不列入勾选**，但每次声明要写明 |

- `declaration` 亦可写成**字符串数组**（简单形态，逐行文字、无分栏）；两种形态生成器都收。
- **缺省声明不阻断生成，但必须留痕**：生成器打 `[WARN]`（声明未做 ＝ 未声明范围；与 SKIP 同纪律）。

**分页轴可配置**（`--split`）：`nature`（**默认**，问题性质）｜`type`（12 类词表的大类）｜`code`（复核域）｜`sev`（严重度）。**`nature` 缺省时自动回退 `type` 大类**，不报错。

**「问题性质」（清单 `nature` 字段）**：报告级分类轴，与 12 类 `type` 词表**不是一套**——`type` 管「是什么毛病」，`nature` 管「报告怎么分派处理」。**推荐五类**：①数据不一致／②表述不一致／③自身逻辑／④格式规范／⑤事实存疑；**项目可自定标签**，但同一报告内须统一。工作表名做 Excel 名净化（去 `[ ] : * ? / \` 五个字符、截 31 字符）；标签命中推荐五类时按其顺序排，否则按条数降序。

**明细列（问题台账）**

**编号｜严重度｜性质｜域｜行号｜原文片段｜问题标题｜问题描述｜建议**（`rev` 存在时追加「定稿文本」、`author` 存在时追加「作者」）

- 「编号」＝ `code` ＋ 该前缀内序号（如 `J-01`）；「域」＝ `code` 本身
- 「行号」＝ `line` 字段（被复核文档的行号或行号区间，如 `340`、`9044-9046`；可缺，缺则留空）
- 「原文片段」＝ `anchor`，**完整不截断**（台账要能直接定位）；「问题描述」＝ `desc`；「建议」＝ `advice`
- 与批注**同源同编号**（清单一次性分配）——报告 ↔ 批注 ↔ 总览 md 三者可互相回溯

**形态纪律**

| 项 | 规则 |
|---|---|
| 载体 | Excel workbook（`.xlsx`）；`openpyxl` 生成、**惰性导入**（仅在触发生成时加载，维持「按载体按需装」） |
| 可读性 | 冻结首行 ＋ 自动筛选 ＋ 表头样式 ＋ 严重度着色（**高＝红系｜中＝橙系｜低＝灰系**——遵中文语境「红＝最需处理」，与股市涨跌配色同源）；封面**仅主标题居中**（其余标题左对齐）、**所有行铺满 A:C 上下等宽** |
| 命名 | `<原文>_<YYYYMMDD>_v<N>_复核报告.xlsx`（G3 轮次规则同批注版：同轮重跑覆盖、跨轮必升 N） |
| 只读生成 | 只消费清单 JSON，**不改原文、不写回清单**；输出分层遵 P10——stdout 只出指标行 ＋ 路径回传，明细在文件里 |
