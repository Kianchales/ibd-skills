# ibd-quality-gates（IBD 投行质量校验）

交稿前的质量校验：**每个数字有来源、每句判断有依据、没有过头话、没有 AI 腔，五项判据全过才放行。**

## 何时使用

| 场景 | 触发词示例 |
|------|-----------|
| 文档写完，交稿前校验 | 「质量校验」「这篇能不能交」「交付前检查」 |
| 检查数字是否可信 | 「数字五要素」「数字有来源吗」「裸数字检查」 |
| 查说过头的话 | 「绝对化扫描」「有没有说大话」 |
| 查 AI 写作痕迹 | 「反模式扫描」「AI 痕迹检查」 |
| 给文档打分 | 「质量自评」「这篇打几分」 |

## 使用流程

> 最小复现示例（对话触发 / 命令 / 期望输出）见 [examples.md](references/examples.md)。

### 第 1 步：动笔前，先把任务想清楚（每个任务都做）

动笔前先答四件事，答不清就先别写：

1. **复述任务**：一句话说清这份文件要解决什么问题、交付物是什么——防写偏
2. **想清风险**：本任务最大的三个坑是什么（比如数据拿不到、口径说不清）——防遗漏
3. **分清数据**：哪些数已经有了、哪些还要去要——防编数
4. **先看资料**：模板、权威口径、同类案例先看一遍再动笔——防闭门造车

> 多角色团队场景的参数差异与写作 Pre-Flight 清单见 [task-core.md](references/task-core.md)。

### 第 2 步：写完后，做四类检查（每类先一句话说清）

**检查一：数字五要素——每个数都要能答五问**

一个数字能不能留在正文，看它能否回答：**多少**（单位）、**什么时候**（时点）、**哪来的**（来源）、**多精确**（精度）、**跟谁比**（可比口径）。答不全的不许留——要么补全，要么明确标「待补」。

> 合格：`2024 年营业收入 11.20 亿元（来源：发行人 2024 年度审计报告）`——单位、时点、来源齐全。
> 不合格：`营收 11.2 亿`——哪年的？谁的？哪来的？都答不上。

**检查二：反模式扫描——照清单给常见的"投行文档病"过一遍**

常见毛病分四类：**数据类**（无来源、口径混用）、**论证类**（观点没支撑、风险不披露）、**表述类**（AI 腔、套话、堆形容词）、**编造类**（红线，出现即整段作废）。完整清单见 [antipatterns.md](references/antipatterns.md)。

**检查三：交稿前自检——10 条逐条过，一条不过不交**

比如：每个数字都有来源吗？有没有"我认为"？前瞻判断附风险提示了吗？完整清单见 [rules.md](references/rules.md) §3。

**检查四：质量自评——给自己打分，低于 25 分回炉**

按数据准确性、合规性、专业深度、逻辑完整性、风险披露、文笔六维打分，每维 5 分、满分 30。**总分低于 25 分，回炉重写，不交付。** 量表见 [rules.md](references/rules.md) §4。

### 第 3 步：交稿前，按五项判据定"能不能交"（G1-G5）

上面的检查是"查的动作"，五项判据是"查完算不算数"的标尺——**任何一项不过，不交付**：

| 校验项 | 白话判据 | 与检查的关系 |
|---|---|---|
| G1 数字可溯源 | 正文每个数字都能答上五要素 | 检查一的通过标尺 |
| G2 无过头话 | 「领先、最优、第一」等绝对化表述一个不留 | 检查二中表述类的子项（词表扫描） |
| G3 引用可追溯 | 每条引用对得上原文——引了什么、编号多少、用在哪个位置 | 引用类问题 |
| G4 依据有对照 | 引用的依据本身核实过（版本、方法论条目编号） | 外部依据核查 |
| G5 自评达标 | 自评 ≥25 分 + 报告随稿交付 | 检查三、四的通过标尺 |

> 详细定义见 [rules.md](references/rules.md) §5。
> **关于 G6**：docx 文件完整性检查（officecli validate + view issues）已移交 `ibd-doc-review` S6 补充门禁（见「与 ibd-doc-review 的分工」）——本 skill 只管内容，不管"文件能不能打开"。

### 第 4 步：执行顺序（照着走即可）

```
初稿完成
  → ① 跑脚本 python scripts/check_gates.py <文件>          # 机器扫：裸数字粗筛 + 绝对化/AI 痕迹
  → ①' 跑脚本 python scripts/check_data.py --input <草稿.md|docx>   # 机器核：金额写法/前后一致/合计勾稽/跨表比对
       （md 草稿阶段就能跑，此刻改的是 md，零排版成本；docx 正式稿复核也能跑）
  → ② 人工过反模式清单 references/antipatterns.md          # 机器扫不了的语义问题，人来核
  → ③ 交稿前自检 10 条逐条过
  → ④ 质量自评打分（6 维 30 分）
  → ⑤ 出「质量自评报告」随文档一起交
```

> 机器扫与人工核的分工：脚本查机械项（词表命中、裸数字、金额写法）；语义项（数字有没有出处、判断有没有依据、风险有没有披露）必须人工按清单核对——脚本替代不了。

### 第 5 步：质量自评报告（随文档交付，附在文末）

```
质量自评报告
- 自评总分：__ /30（数据准确性 _/5 · 合规性 _/5 · 专业深度 _/5 · 逻辑完整性 _/5 · 风险披露 _/5 · 文笔 _/5）
- 校验状态：G1 __ | G2 __ | G3 __ | G4 __ | G5 __
- 反模式命中：无 / 命中 __ 条已修复（清单）
- 遗留「待补」项：__ 处（位置清单）
```

### 第 6 步：关于 G4——引用要能对得上依据

凡引了外部资料——研究报告、法规条款、他人观点、方法论条目——都要能回答三个问题：**引了什么、出处编号是多少、用在正文哪个位置**。交付前附一张对照表。

如果你维护自己的方法论索引（「问题类型 → 条目编号」的映射表），把它放进用户级配置 `~/.config/gates-index.json`（格式：`{"名称": "索引文件路径"}`），G4 会按你的索引核对；没有这个文件就按通用规则人工核对，不影响其他模块。

## 依赖与工具

> **本 skill 独立可用**——不依赖团队配置、不依赖知识库，装上就能用。

| 维度 | 说明 |
|---|---|
| 🔴 **必须** | **无第三方依赖**（check_gates.py / check_data.py 仅用 Python 3 标准库，零 pip 包） |
| 🟡 **推荐** | 知识库（检索同类案例做对比，增强判断依据）；金融数据终端（数字交叉验证）——都没有也能跑，规则全量执行 |
| 🟢 **可选** | 方法论库 `{METHODS_ROOT}`（G4 来源对照更严，无库按通用规则人工核对）；`ibd-doc-review`（格式问题移交出口，数值核对已内置本 skill，不依赖它） |
| **运行模式** | 单人直接用；多角色团队中作为全员公共质量校验层 |

### 工具说明（每个工具为什么是现在这个层级）

**🔴 必须 · Python 3**
- 规则全内置，脚本只用标准库（re/zipfile/argparse）——装上就能跑，不污染环境

**🟡 推荐 · 知识库（KB_BACKEND）**
- 用途：检索同类案例做对比参考（动笔前「先看资料」的加载对象）
- 为什么只是推荐：有案例参照，判断更有依据；没有，跳过加载步骤，规则照跑

**🟡 推荐 · 金融数据终端**
- 用途：数字交叉验证（给数字五要素的"哪来的"加一道外部印证）
- 为什么只是推荐：没有就用文档自身的来源标注，人工判断兜底

**🟢 可选 · 方法论库 `{METHODS_ROOT}`**
- 用途：G4 来源对照更严（引用的条目编号能精确核对）
- 为什么只是可选：无库按通用规则人工核对，校验仍有效

**🟢 可选 · `ibd-doc-review`**
- 用途：格式/样式问题（序号、表格样式、排版）的移交出口
- 为什么只是可选：本 skill 只报内容问题、不查排版；数值核对已内置，不依赖 review

## 边界与协作

| 检查项 | 归属 |
|--------|------|
| 排版样式、标题序号、标点、表格规范 | `ibd-doc-review` |
| 金额在表格里的样子（对齐/字号/合计加粗） | `ibd-doc-review`（table 组） |
| 金额的写法（千分位/小数位）、数值前后一致、合计勾稽 | **本 skill**（check_data.py；md 草稿即可跑） |
| 数字有没有来源和口径 | **本 skill** |
| 观点有没有论据、风险有没有披露 | **本 skill** |
| 过头话（"领先/最优/第一"） | **本 skill**（词表独有） |
| AI 写作痕迹、套话堆砌 | **本 skill** |
| 文件本身能否打开（OpenXML 合法性/文本溢出等物理缺陷） | `ibd-doc-review`（S6 补充门禁） |

推荐顺序：初稿（md）→ 本 skill 过质量校验（脚本 + 四类检查 + 五项判据）→ 样式化定稿 → `ibd-doc-review` 查格式 → 交付。

规则修改只改本 skill；多角色团队配置中已收敛为指针，不重复维护。
